## §1 문제 명확화 — 변수 분리

### 호출자의 현재 가설

1. lerobot 의 pyav video decode 경로에서 frame buffer 가 release 되지 않아 시간 비례 선형 누수 (main process 아닌 worker 또는 OS-level buffer 에서)
2. DataLoader workers 가 주범 → num_workers 축소로 해소 가능 (→ 시도 2 가 부분 반박)
3. 동시 점유 프로세스 (VSCode, Claude Code agent, Firefox) 가 OOM 가속

### 직접 증명된 부분

- wandb 시도 1: System Memory Utilization 10% → 100% 선형 증가 (20분), main process RSS 3.4 GB 고정 — main process 무관 확정
- dmesg: `CONSTRAINT_NONE / global_oom` — cgroup 한도 아님, UMA 128GB 전체 부족 확정
- dmesg: `task=code` 2회 OOM-kill — VSCode server 가 상당 메모리 점유 확정
- 시도 2 (workers 8→2): steady-state 누수 1,805 → 1,254 MB/min (30% 감소만) — workers 수 자체는 주범 아님
- ffprobe: leftarm_v2 mp4 14개 전부 h264 — codec mix 가설 부정

### 추정만 된 부분 (미검증)

- v1 (40ep, libsvtav1) 완주 vs v2 (110ep, h264) OOM 의 결정적 변수 (cleanup 상태가 달랐을 가능성, 동시 점유량 차이)
- 시도 2 에서 cleanup 이 실제로 충분히 이루어졌는지 (training_log.md 시도 2 에 cleanup 지시는 있으나 실제 프로세스 kill 확인 기록 없음)
- pyav 의 C 레벨 libavcodec 내부 버퍼가 GC 우회해 OS 에 잔류하는지 여부
- num_workers=0 단일 프로세스에서도 동일 누수가 발생하는지 (미실험)

### v1 완주 vs v2 OOM — 변수 분리 분석

| 변수 | v1 | v2 | OOM 기여 가능성 |
|---|---|---|---|
| 에피소드 수 | 40ep | 100ep (2A subset) | 낮음 — main process 3.4 GB 안정, dataset metadata 만이라 크기 영향 미미 |
| step 수 | 5,000 | 20,000 | 낮음 — 사망이 step 368 (epoch 0.1 미만), step 수 자체 무관 |
| codec | libsvtav1 | h264 (전부 확인) | 중간 — h264 는 delta-frame 구간이 libsvtav1 보다 길 수 있음 (GOP interval 차이), 더 많은 프레임 순차 디코딩 필요 |
| num_workers | 8 | 8 (시도 1), 2 (시도 2) | 중간 — workers 수 줄여도 30% 만 감소, workers 자체는 주범 아님 |
| 동시 점유 | 기록 없음 | VSCode + Claude Code + 기타 확인됨 | **높음** — dmesg 가 VSCode 2회 kill, 학습 시 환경 점유 상태 v1 시점 기록 없어 비교 불가 |
| prefetch_factor | 2 | 2 (시도 1), 1 (시도 2) | 낮음 — 시도 2 에서 1로 줄여도 30% 감소만 |

**결정타 식별**: 현 증거로 결정타를 단일 변수로 지정할 수 없다. 가장 강한 신호는 두 가지의 복합:
- (A) pyav video decode 자체의 worker/OS-level 버퍼 누수 (시간 비례 고정 누수율이 핵심 증거 — workers 와 무관)
- (B) 동시 점유 (VSCode + Claude Code agent) 가 baseline 을 올려 OOM zone 도달 시간 단축

### pyav leak 가설 — 코드 리뷰 직접 증명

`decode_video_frames_torchvision` (video_utils.py L156-260) 의 pyav 경로:

```python
torchvision.set_video_backend(backend)   # "pyav"
if backend == "pyav":
    keyframes_only = True  # pyav doesn't support accurate seek

reader = torchvision.io.VideoReader(video_path, "video")
reader.seek(first_ts, keyframes_only=keyframes_only)  # 키프레임으로 seek

for frame in reader:
    loaded_frames.append(frame["data"])
    if current_ts >= last_ts:
        break

if backend == "pyav":
    reader.container.close()   # container 만 close
reader = None                  # reader 는 None 으로 해제 시도 (GC 의존)
```

**코드 리뷰 결과 — leak 가설 지지 (중간~강함)**:

1. **keyframes_only=True 의 의미**: pyav 는 정확한 seek 미지원 → 키프레임부터 순차 디코딩. `first_ts` 가 키프레임이 아니라면 키프레임 ~ `first_ts` 구간의 중간 프레임들을 모두 디코딩해 `loaded_frames` 에 append. GOP 기본값 g=2 이면 2프레임마다 키프레임이지만, 실제 녹화된 영상의 GOP 가 길면 수십 프레임을 항상 추가 디코딩.

2. **close 불완전성**: `reader.container.close()` 는 호출되지만 `reader` 자체는 `None` 으로 설정 후 GC 의존. PyAV GitHub Issue #1117 에서 확인: "PyAV has a number of reference cycles that make it more difficult for the garbage collector... In tight loops involving opening many containers, a Container will not auto-close until many a few thousand have built-up." — PyAV 의 C 레벨 Cython wrapper 에서 참조 사이클이 GC 우회 가능.

3. **DataLoader worker 내 반복 호출**: 각 배치마다 `decode_video_frames_torchvision` 이 호출 → 매 호출마다 새 `VideoReader` 생성 → container.close() + reader=None 후 GC 에 의존하지만, worker 프로세스는 OS 에 메모리를 즉시 반환하지 않을 수 있음 (glibc malloc arena 누적).

4. **stream.close() 누락**: PyAV Issue #1117 fix 는 `stream.close()` 와 `stream.codec_context.close()` 를 명시적으로 호출해야 한다고 지적. 현재 lerobot 코드는 `reader.container.close()` 만 호출하고 stream 은 명시 close 안 함.

**결론**: pyav leak 가설은 코드 구조상 타당하다. 단 "pyav 버그" 라기보다 **lerobot 의 불완전한 close 패턴 + GC 의존 + worker 프로세스의 OS malloc 반환 지연** 의 복합. 완전한 직접 증명은 `num_workers=0` 실험이 필요.

### lerobot upstream commit history 분석

`git log --grep="memory|leak|video|decode|pyav"` 로 관련 commit 확인:

### num_workers=0 실험 제안

**이 단일 실험이 가설을 가장 효율적으로 분리할 수 있다**:
- num_workers=0 에서도 누수 발생 → workers 무관, pyav 자체 또는 OS malloc 이 주범 → cleanup 은 답 아님
- num_workers=0 에서 누수 없음 → workers/IPC 가 누수 경로 → num_workers=0 + cleanup 조합이 해결책
- 예상 소요: 30분 (OOM 발생 여부 확인 시간) + cleanup 5분

## §2 외부 사례 검색

### 2-1. GitHub Issues — lerobot upstream

**Issue #2209**: [std::bad_alloc / DataLoader worker exited unexpectedly during training with smolvla_base](https://github.com/huggingface/lerobot/issues/2209)
- 관련도: **높음** — smolvla_base 학습 중 DataLoader worker 가 `std::bad_alloc` 으로 crash. `num_workers=0` + `prefetch_factor` 제거로 해결 (학습은 가능, 느림). PyTorch 2.9 nightly + dual 96GB GPU 환경.
- 우리 환경과의 차이: 우리는 worker crash 아닌 system OOM. 하지만 같은 pyav 경로의 메모리 문제임.

**Issue #1623**: [Slow video decoding](https://github.com/huggingface/lerobot/issues/1623)
- 관련도: **중간** — AV1 디코딩이 H.264/image 대비 5× 느림. 메모리 누수 언급 없음. 우리는 h264 사용 중이라 속도 문제는 다르나, image dataset 이 video 대비 훨씬 빠른 것은 확인.
- 발견: "Image-based loading: 7-43ms vs AV1: 220-240ms". H.264: 15-18ms.

**Issue #1488**: [Dataloader blazingly fast for ACT but VERY slow for SmolVLA](https://github.com/huggingface/lerobot/issues/1488)
- 관련도: **중간** — SmolVLA 학습 시 dataloader 가 backprop(0.7s) 보다 오래 걸림(1s). num_workers 16+ 에서 worker crash. 메모리 누수 직접 언급 없음.

**Issue #2488**: [Multiprocessing leads to decoding error](https://github.com/huggingface/lerobot/issues/2488)
- 관련도: **중간** — num_workers=4 에서 "Invalid data found when processing input" torchcodec 에러. num_workers=1 로 해결. multiprocessing + video decode 의 thread-safety 문제 시사.

### 2-2. PyAV GitHub Issues

**Issue #1117**: [Memory leak if stream is not explicitly closed](https://github.com/PyAV-Org/PyAV/issues/1117)
- 관련도: **높음** — container.close() 만으로는 부족, stream 도 명시 close 필요. 현재 lerobot 코드가 이 패턴을 적용하지 않음. PyAV 12.x 에서 일부 fix.

**Issue #317**: [Memory leak while reading frames from preloaded video buffer](https://github.com/mikeboers/PyAV/issues/317)
- 관련도: **높음** — "반복 루프에서 container 를 많이 열면 GC 가 수천 개가 쌓여야 auto-close 하는 reference cycle 문제".

**Issue #778**: [Memory Leak Writing Iterator of Numpy Arrays to Disk](https://github.com/PyAV-Org/PyAV/issues/778)
- 관련도: **중간** — numpy 배열이 container close 전까지 해제 안 됨 → 무한 메모리 증가 → OOM. 패턴이 우리 케이스와 유사.

**Discussion #1599**: [Memory leak if stream is not explicitly closed](https://github.com/PyAV-Org/PyAV/discussions/1599)
- 관련도: **높음** — "Python 3.10 + PyAV 14 이상에서 개선" 하지만 "tight loop 에서는 여전히 명시 close 권장".

### 2-3. torchcodec aarch64 지원 상태

**Issue #1251**: [Torchcodec wheel package is not available for Aarch64 platform](https://github.com/meta-pytorch/torchcodec/issues/1251)

**Issue #569 / #937**: aarch64 지원 요청 — 공식 타임라인 없음, 오픈 상태.

### 2-4. DGX Spark aarch64 환경

- [natolambert/dgx-spark-setup](https://github.com/natolambert/dgx-spark-setup): PyTorch 2.9+ cu130 (CUDA 13.0) 권장. 현재 우리 환경은 PyTorch 2.10 + CUDA 12.1 — 이는 NVIDIA 공식 DGX Spark 최신 PyTorch 이나 cu130 이 아님. torchcodec, video decoding 관련 언급 없음.

## §3 직접 증거 — lerobot video_utils.py 코드 리뷰

### 핵심 함수: `decode_video_frames_torchvision` (L156-260)

**pyav 경로의 leak 가설 지지 코드 패턴**:

```python
# L193: 매 decode 호출마다 새 VideoReader 생성
reader = torchvision.io.VideoReader(video_path, "video")

# L188-189: pyav 는 keyframes_only=True
# → 요청 timestamp 전 키프레임부터 순차 디코딩 → 중간 프레임들도 loaded_frames 에 누적
if backend == "pyav":
    keyframes_only = True

# L203: keyframe seek
reader.seek(first_ts, keyframes_only=keyframes_only)

# L208-215: 키프레임부터 last_ts 까지 모든 프레임을 loaded_frames 에 append
for frame in reader:
    loaded_frames.append(frame["data"])
    if current_ts >= last_ts:
        break

# L217-218: container.close() 는 있음
if backend == "pyav":
    reader.container.close()

# L220: reader = None — GC 의존 (stream.close() 없음)
reader = None
```

**문제점 3가지**:

1. **stream.close() 누락**: container.close() 만 호출, `reader.container.streams.video[0].close()` 없음. PyAV Issue #1117 에서 stream 명시 close 가 메모리 누수 방지에 필수임을 확인.

2. **loaded_frames 중간 프레임 누적**: keyframes_only=True 로 seek 하면 요청 timestamp 앞의 GOP 전체 프레임을 디코딩. GOP=2 (default) 면 영향 적지만, 인코딩 시 GOP 가 더 크게 설정되면 수십 프레임 중간 디코딩. `loaded_frames` 는 함수 반환 전 일부만 사용되나 나머지는 GC 에 의존.

3. **GC 타이밍 불확실성**: DataLoader worker 프로세스에서는 GC 가 메인과 독립적으로 동작. worker 가 C 레벨 PyAV 객체의 reference cycle 을 즉시 해소하지 못하면 OS 에 메모리 반환이 지연. 이 지연이 누수처럼 보임.

### `VideoDecoderCache` (L263-309) — torchcodec 전용

- torchcodec 경로에는 `VideoDecoderCache` 가 존재해 decoder 를 재사용하고 file handle 을 추적·close. pyav 경로에는 이 cache 가 없음. 매 decode 호출마다 새 연결 생성.

### streaming_dataset.py

- `_query_videos` (L546-567): `decode_video_frames_torchcodec` 만 호출 — streaming dataset 은 torchcodec 전용. pyav 를 사용하지 않음.
- **결론**: streaming dataset 을 사용해도 우리 DGX 환경에서는 torchcodec ABI 미스매치로 import 단에서 실패.

### upstream commit 의 leak 관련 개선

- `a8b72d96` (2026-04-19): `return_uint8` 추가 (IPC 메모리 최적화). pyav close 패턴 자체는 미변경.
- leak fix commit 없음 확정.

### 옵션 상세

#### 옵션 1: 환경 cleanup 강화 (VSCode/Firefox/Claude Code 완전 종료)

- **동작 원리**: dmesg 에서 VSCode (`code`) 가 2회 OOM-kill 된 것이 직접 증거. VSCode server (code-server + extension host), Claude Code agent worker, Firefox 가 합산 30~60GB 점유 가능. 학습 전 이를 완전 종료하면 여유 메모리가 늘어 leak 속도가 같아도 OOM zone 도달에 더 많은 시간 필요. v1 완주의 핵심 차이가 이것일 가능성.
- **검증 방법**: 종료 전 `free -h` → 종료 후 `free -h` 로 회수된 메모리 확인. 학습 30분 이상 OOM 없으면 성공.
- **미탐색 의문점**: cleanup 이 충분히 이루어졌는지 시도 2 에서 기록이 불완전. training_log.md 에 "cleanup 필수" 지시는 있으나 실제 kill 결과 확인 없음.
- **재시도 비용**: 실패해도 시간 30분 + 정보 획득 (cleanup 가 답 아닌 것 확정).

#### 옵션 2: num_workers=0 으로 시도 3

- **동작 원리**: workers=0 이면 main process 가 직접 decode. DataLoader IPC shmem 없음 → workers 경유 GC 불확실성 제거. 만약 누수가 멈추면 workers + pyav GC 복합이 원인 확정. 계속 누수되면 pyav 자체 또는 OS malloc 이 원인.
- **검증 방법**: MemAvailable 30분 관찰. 누수 없으면 가설 확정.
- **미탐색 의문점**: workers=0 은 학습 5~10x 느릴 수 있어 20,000 step 완주에 수일 소요 — 실용적 해결책 아님 (가설 확정 도구).
- **재시도 비용**: 30분 관찰 + 가설 분리 완료.

#### 옵션 3: image dataset 변환 (현 잠정 결정)

- **동작 원리**: video decode 경로 완전 우회. 학습 중 mp4 를 전혀 열지 않음 → pyav 관련 leak 근본 제거. lerobot 이 PNG/JPEG 를 직접 load — 훨씬 간단한 경로.
- **검증 방법**: 학습 30분 OOM 없음 + memory 안정적 (MemAvailable 변화 <10%).
- **미탐색 의문점**: 변환 스크립트 작성 + 110ep 변환 시간 (예상 2~4시간). 디스크 추가 사용량 (110ep × 2 cam × 540frames × 640×480 JPEG ≈ 예상 20~50GB 추가).
- **후속 영향**: 원본 leftarm_v2 보존. 향후 rightarm 등 다른 dataset 에 재사용 가능. M2 학습 속도는 image loading 이 video decode 보다 일반적으로 빠름.

#### 옵션 4: pyav close 패턴 monkey-patch

- **동작 원리**: `lerobot/datasets/video_utils.py` 의 `decode_video_frames_torchvision` 을 monkey-patch 해 `stream.close()` 와 `gc.collect()` 를 명시 호출. `docs/reference/lerobot/` 는 Cat A read-only 이므로 별도 wrapper 스크립트에서 monkey-patch 적용.
- **검증 방법**: 패치 후 학습 30분 OOM 없음.
- **미탐색 의문점**: `reader.container.streams.video[0]` 접근이 torchvision VideoReader 에서 가능한지 확인 필요. GC 강제 호출이 학습 속도에 영향 줄 수 있음.
- **후속 영향**: lerobot 업데이트마다 재검증 필요. Cat A 코드 직접 수정 아니므로 Category B 에 해당하지 않음 — 단 별도 wrapper 파일 관리 오버헤드.

#### 옵션 5: --dataset.streaming=true

- **동작 원리**: streaming_dataset.py 는 decode_video_frames_torchcodec 만 사용 (pyav 우회). 단 DGX 환경에서 torchcodec ABI 미스매치 → import 단 실패.
- **검증 방법**: import 성공 여부 확인 먼저 필요.
- **미탐색 의문점**: aarch64 비공식 wheel (time2k/torchcodec_for_aarch64) 이 우리 PyTorch 2.10 + FFmpeg 6 과 호환되는지 미확인.
- **결론**: DGX 환경에서 현재 비현실적.

#### 옵션 6: mp4 chunk 재인코딩 (GOP 조정)

- **동작 원리**: GOP 크기를 줄여 (g=1 또는 g=2 → g=1) 각 seek 시 디코딩해야 하는 중간 프레임 수 감소. 단 이미 g=2 (default) 라 추가 효과 미미. keyframes_only 경로의 중간 프레임 누적은 여전히 발생.
- **검증 방법**: 재인코딩 후 학습 30분 누수율 비교.
- **결론**: 효과 불확실, 비용 높음. 우선순위 낮음.

#### 옵션 7: DGX 환경 다운그레이드 (PyTorch 2.9 + CUDA 13.0)

- **동작 원리**: torchcodec aarch64 지원이 추가되면 (또는 비공식 wheel 사용) pyav 우회 가능. 단 현재 torchcodec 공식 aarch64 지원 없음 (Issue #1251 오픈), PyTorch 2.9 + CUDA 13.0 재설치 후에도 torchcodec 이 동작할 보장 없음.
- **검증 방법**: torchcodec import 성공 + lerobot decode 테스트.
- **결론**: 리스크 대비 효과 불확실. 장기 Backlog 적합.

## §5 추천 + 근거 + 최소 비용 검증 제안

### 추천 — 2단계 순차 접근 (빠른 실험 먼저)

**1단계 (최소 비용 검증, 약 45분): 옵션 1 + 2 병렬**

옵션 3 (image 변환) 은 3~6시간 작업이다. 그전에 45분짜리 실험 2개로 원인을 확정하면 의사결정 위험이 줄어든다.

- **실험 A** — cleanup 강화 + 시도 3:
  1. 학습 시작 전 `pkill -9 -f code`, `pkill -9 -f claude`, Firefox 완전 종료
  2. `free -h` 로 available 확인 (100GB+ 여야 함)
  3. num_workers=2, prefetch=1 유지하고 학습 시작
  4. 30분 관찰: OOM 없으면 옵션 3 불요 — 동시 점유가 결정타

- **실험 B** — num_workers=0 가설 확정 (실험 A 와 별개 또는 실험 A 실패 후):
  1. cleanup 강화 상태에서 num_workers=0 으로 30분 관찰
  2. 누수 없으면 workers + pyav GC 복합 확정 → monkey-patch 고려
  3. 누수 있으면 pyav 자체가 원인 → image 변환만이 답

**2단계 (실험 결과 따라)**:
- 실험 A 성공 (cleanup 만으로 해결) → image 변환 불요. `RECOMMENDS_ALTERNATIVE`.
- 실험 A 실패 + 실험 B 성공 (workers=0 해결) → monkey-patch 또는 image 변환 중 선택.
- 실험 A, B 모두 실패 → image 변환이 유일한 안정적 옵션 → `NO_BLOCKER` (image 변환 결정 confirm).

### 단일 추천 (사용자가 최소 비용 검증을 원하지 않는 경우)

**옵션 3 (image dataset 변환) — 유지**.
- 근거 1: 가장 효과 확실 (90%+). video decode 경로 완전 우회.
- 근거 2: 다른 옵션들 (cleanup, patch, streaming) 은 효과가 50% 미만이거나 환경 제약으로 불가.
- 근거 3: 재사용성 — 향후 rightarm dataset 에도 적용.
- 근거 4: 우리 환경 (aarch64, PyTorch 2.10, FFmpeg 6) 에서 torchcodec 미사용으로 대안 backend 없음.
- **Plan B**: 이미지 변환 후에도 OOM 발생하면 (다른 원인 존재 시) → monkey-patch (옵션 4) 추가.

### 최소 비용 검증 제안 (DOD(d) 의무 이행)

```
실험 A — 환경 cleanup 강화 + 시도 3
예상 소요: 준비 10분 + 관찰 30분 = 40분
비용: 제로 (재인코딩·스크립트 없음)
확인 방법:
  1. 시작 전: `free -h` → MemAvailable > 100 GB 확인
  2. `pkill -9 -f code` + `pkill -9 -f claude` + Firefox 종료 + `sync && echo 3 > /proc/sys/vm/drop_caches` (sudo 필요시 사용자 수행)
  3. 학습 시작, 30분 모니터링: `watch -n 30 'free -h | grep Mem'`
  4. MemAvailable 이 90 GB 이상 유지되면 → cleanup 이 결정타 (image 변환 불요)
  5. 급락하면 → pyav leak 확정 → image 변환 진행

실험 B — num_workers=0 단일 프로세스 가설 확정 (옵션, 실험 A 후)
예상 소요: 15분 설정 + 30분 관찰 = 45분
비용: 학습 매우 느림 (실용 목적 아님, 진단 전용)
확인 방법: 위와 동일한 memory monitoring, 누수 없으면 workers 경유 leak 확정
```

### 사용자 결정 필요 사항

1. **실험 A 먼저 시도할 의사가 있는가?** — 있으면 image 변환 전에 40분 투자. 없으면 image 변환 직행.
2. **실험 B (num_workers=0 느린 학습) 를 진단 목적으로 허용하는가?** — 없어도 image 변환으로 진행 가능.

## 핵심 발견 요약 (메인 Claude 에게)

### 가장 강력한 새 증거

**1. lerobot video_utils.py 코드 리뷰 — stream.close() 누락 확인**
- `decode_video_frames_torchvision` 이 `reader.container.close()` 는 하지만 `stream.close()` 는 없음.
- PyAV Issue #1117 에서 stream 명시 close 없이 GC 의존 → reference cycle 로 인해 수천 개의 container 가 쌓여야 auto-close 되는 문제 확인.
- 매 배치마다 VideoReader 를 새로 생성하는 패턴 + pyav keyframes_only seek (중간 프레임 dicard 불완전) = 시간 비례 선형 누수의 코드 레벨 근거.

**2. PyAV Issues #317, #1117 — DataLoader loop 에서의 알려진 패턴**
- "tight loop involving opening many containers → GC 가 수천 개 쌓여야 auto-close" — 우리 학습이 20,000 step 이면 수만 번 container 생성 → 정확히 이 패턴.
- PyAV 12.x 이후 개선됐으나 우리 pyav 15.1.0 에서도 stream 명시 close 없는 패턴은 여전히 위험.

**3. lerobot streaming_dataset 는 torchcodec 전용 — DGX 에서 불가 확정**
- streaming_dataset.py L557: `decode_video_frames_torchcodec` 만 호출. pyav fallback 없음.
- 옵션 5 (streaming) 는 DGX 환경에서 현실적 대안 아님 — 확정.

## verdict

`VERDICT: NEEDS_INVESTIGATION`

image 변환 결정 자체는 타당하나, 실험 A (환경 cleanup 강화) 를 먼저 40분 시도하는 것이 강력히 권장된다. v1 완주 vs v2 OOM 의 차이가 동시 점유량 차이일 가능성이 증거 기반으로 상당하며 (dmesg VSCode 2회 kill 직접 증거), 이 실험이 성공하면 3~6시간 image 변환 작업을 절약할 수 있다. 실험 A 실패 시 image 변환 결정 confirm (`NO_BLOCKER` 로 전환).
