## 🚨 핸드오프 — 보드 #4 (CAN ID 11, left_ankle_pitch) RDP 차단 상태

> **상황**: 2026-05-12 약 20:40, 사용자 babogaeguri 가 보드 D (CAN ID 11, MAD 5010) 작업 중 Run #3 단계에서 차단됨. 보드의 STM32G431 칩이 **RDP Level 1** (Read Out Protection) 활성화 상태로 진입해 IDE 의 `Run` 도, CLI 의 `-d` (다운로드) 도, `-e all` (mass erase) 도 모두 `failed to erase memory` 로 실패. 담당자가 다른 팀원으로 변경됨.

### 현재 상태 요약

- **보드 시리얼**: ST-LINK SN `0668FF515266555067014751` (보드 #4)
- **보드 이름**: B-G431B-ESC1 (left_ankle_pitch 용)
- **목표 CAN ID**: 11
- **목표 모터 프로파일**: `MOTORPROFILE_MAD_5010_110KV`
- **진행 단계**: Run #1 ✅, Run #2 ✅, **Run #3 ❌ (차단)**
- **연결**: ST-LINK 연결·통신 정상 (`-c port=SWD mode=UR reset=HWrst` 통과)
- **차단 원인**: Option byte `RDP : 0xFF (Level 1, read protection of memories)`
- **WRP**: 정상 (STRT > END = 비활성)
- **PCROP_RDP**: 0x1 — RDP 낮춰지면 PCROP zone 도 자동 erase

### 진단 결과 (CLI 출력 기록)

`STM32_Programmer_CLI -c port=SWD mode=UR reset=HWrst -ob displ` 결과:

```
RDP          : 0xFF (Level 1, read protection of memories)
WRP1A_STRT   : 0x3F  (0x801F800)
WRP1A_END    : 0x0  (0x8000000)        ← STRT > END = WRP 비활성
WRP1B_STRT   : 0x3F  (0x801F800)
WRP1B_END    : 0x0  (0x8000000)        ← 동일, WRP 비활성
PCROP1_STRT  : 0x3FFF  (0x801FFF8)
PCROP1_END   : 0x3FFF  (0x8020000)
PCROP_RDP    : 0x1 (PCROP zone is erased when RDP is decreased)
SEC_SIZE1    : 0x40  (0x8020000)
BOOT_LOCK    : 0x1
```

## 환경 특이사항 / 주의

1. **OS 차이**: 절차서는 Windows 기준이지만 Linux 도 동일하게 동작. 다만:
   - Windows 의 "차단 해제" / "관리자 권한" 같은 항목은 Linux 에서 무관
   - ST-LINK 인식 안 될 시 udev 규칙 추가 필요할 수 있음 (일단 미발생)
2. **경로 정책**: 빌드 영향 영역(`/opt/st/`, 워크스페이스) 은 ASCII + 공백 없음. 문서·로그는 한글 경로 OK.
3. **모터 프로파일 기본값**: GitHub 의 코드는 처음부터 `MOTORPROFILE_MAD_M6C12_150KV` 가 활성 → M6C12 보드 (8개) 는 프로파일 변경 불요. 5010 보드 (4개) 만 프로파일 교체 필요.
4. **Linux 전용 GCC 경고**: 빌드 시 `arm-none-eabi-ld: warning: ... has a LOAD segment with RWX permissions` 출력되지만 STM32 펌웨어에선 정상.

| 증상 | 원인 | 해결 |
|---|---|---|

| `unzip` 풀고 보니 `.exe` 파일 | Windows 용 받음 | OS 셀렉터 Debian Linux 로 재다운로드 |
| `dpkg lock` 권한 에러 | 일반 사용자 권한 | `sudo` 붙여 재실행 |
| `stm32cubeide: command not found` | PATH 미등록 | `~/.bashrc` 에 PATH 추가 |
| `motor_controller.c:98 sprintf implicit declaration` | 펌웨어의 알려진 버그 | `#include <stdio.h>` 추가 |
| 보드 빨간 LED 켜지지만 `lsusb` 에 ST 안 보임 | 충전 전용 케이블 (D+/D- 죽음) 또는 USB 3.0 포트 호환성 / 단자 헐거움 | ① 데이터 케이블 교체 ② 단자 재연결 ③ USB 2.0 포트로 이동 ④ 허브 거치지 말고 PC 직접 |
| ST-LINK V3 빨간 LED **깜빡임** + `dmesg -W` 시 뽑/꽂 이벤트 X | 빨간 깜빡 = "USB host enumeration 실패" 자체 신호. 호스트가 디바이스를 전혀 못 봄 = HW 단절 | 케이블을 스마트폰에 꽂아 PC 인식 여부로 데이터 케이블 / 충전 전용 1차 판별 |
| 케이블 교체해도 lsusb ST 안 잡힘 + 노트북 USB-C only → 허브 거쳐 연결 중 | ~~USB-C 허브 호환성~~ → **메인 오진단**. 같은 허브로 팀원 정상 작동. 진짜 원인: **두 케이블 모두 충전 전용/데이터 단절** | 팀원의 검증된 데이터 케이블 빌려 즉시 확인, 또는 새 데이터 케이블 (스마트폰 인식 검증 필수) |
| Run 중 `Error: failed to erase memory` + `Error in STM32CubeProgrammer` | 타겟 칩 ↔ 디버거 일시 통신 불안정. USB 재연결 너무 짧거나 보드 펌웨어 실행 중 디버거 거부 | USB 뽑기 → **5~10초 대기 (길게)** → 다시 꽂기 → Run 재시도. 거의 항상 1회로 해결 |
| `failed to erase memory` 가 USB 재연결·IDE 재시작·CLI 시도까지 다 실패 | 보드 RDP (Read Out Protection) Level 1 활성화로 erase 차단 | 1) `... -ob displ` 로 RDP 값 확인 (0xFF/0xBB = Level 1) → 2) `... -ob RDP=0xAA` 로 regression (자동 mass erase) → 3) USB power cycle → 4) Run #1·#2·#3 처음부터. **0xCC = Level 2 면 영구, 칩 교체 필요** |
